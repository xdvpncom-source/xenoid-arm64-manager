# v0.1.44 — compatible official-input recovery during rolling updates

This release includes the official touchscreen-registration recovery and physical-capacity calculation from the v0.1.43 candidate. It also preserves compatibility with long-running Python workers: if a resource or profile caller loads while that worker still has the earlier `qa_fresh6a` module cached, it uses the existing read-only verifier. Workers loading the current module use the explicit guarded input-recovery path. No forced restart of all existing workers is required for source publication.

The input fix addresses a valid official uinput device missing from Android's EventHub and InputReader. Explicit resource/profile actions may reannounce the same validated event inode, then require the original service, kernel, EventHub and coordinate proofs. Read-only verification remains read-only. There is no ADB input fallback, new input driver, APK modification or device-identity change. The controlled affected-device test completed recovery in 13.66 seconds without a pointer event; the same inode, service binding, 13 native identities, Build, container, image and resource limits were retained. A second healthy invocation did not request repair.

Default capacity reserves one GiB of physical RAM and the existing host CPU allowance. Complete device slots still require one CPU and two GiB of physical RAM; swap does not increase that count. The measured 22-host fleet therefore permits 70 slots: three on each of the 21 smaller hosts and seven on the larger host. Device creation and application-loop observations are validated separately from this capacity calculation.

Regression tests cover both cached-old and current module dispatch, missing registration, immutable-profile and runtime changes, wrong-node evidence, healthy no-op behavior and physical resource bounds. Normal application-loop and fleet-rollout results are recorded separately.
