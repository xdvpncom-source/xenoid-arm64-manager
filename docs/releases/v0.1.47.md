# v0.1.47 — wait after VPN permission before dismissing the ad

The shared assigned-app scenario now opens the app and handles observed startup notification, consent and terms dialogs before selecting its observed Connect control. Android VPN approval comes next. The scenario then waits a random 90–120 seconds before dismissing ads, keeps the app foreground for ten more seconds while handling new popups, and closes and clears the assigned app.

The post-permission wait leaves ad controls untouched. A nonblocking startup banner is also retained when the Connect control is visible; a blocking startup overlay can still be handled so the assigned app can be reached. Permission confirmation is read from Android's existing VPN app-op state and does not claim proof of a successful network tunnel. The optional `CONNECTED_WAIT_SECONDS` setting remains available as an extra post-permission dwell and defaults to zero.

Some ads open a configured external store without a close-button tap. The scenario records a genuinely observed, owned ad activity during the post-permission dwell and may return from that store only after the dwell finishes, using the existing bounded official Android Back action. It then prefers an observed Close control on the returned ad. An unrelated store page, missing provenance or unproven navigation remains ineligible.

Ad selection first enumerates observed controls, including disabled status, and automatically chooses an eligible Close, Dismiss, X or Skip control. Disabled controls and positive countdown labels are not clicked. A real enabled Close takes priority over decorative progress; changing countdown/progress postpones fallback. Unknown or stalled progress uses the script's configurable wait budgets before the logged, verified Back fallback. The additive SDK helpers `clickable_controls` and `click_control` expose the same inventory and fresh-read native selection without adding manual panel UI.

Official Xenoid input, assigned-package resolution, execution settings, cleanup behavior and the successful-cycle regeneration method are preserved. The regeneration draw remains 1–10 with a trigger of 5, and still follows successful app cleanup. The generic editor SDK template is unchanged; updating a saved shared scenario is a separate panel operation.

Pending native regeneration recovery now loads the original run's saved source and reservation setting instead of borrowing a new scenario revision. It verifies the original run, device binding and recorded scenario/profile context before replay; missing or inconsistent original metadata fails closed. This replays the recorded operation without executing the old user script. Existing current-run admission and identity-acknowledgement rules remain intact, so deployment must still drain native identity operations before replacing their owning run.

Regression tests exercise the full startup-to-cleanup order, retained ads during permission and dwell, visible Connect beside a nonblocking banner, late popups and unchanged cleanup-before-regeneration ordering. Live assigned-APK qualification is recorded separately from source tests.

The real assigned-APK canary completed one cycle with seven official taps, five enumerated control rows and successful app-data cleanup. It requested a 99-second post-permission dwell; the first ad-close action occurred 104.395 seconds after permission confirmation, and the final foreground hold lasted 22.881 seconds before app close. One transient `stock_dump_no_xml` read recovered. VPN permission was already authorized, so this run did not tap that approval dialog. It did not encounter UMP consent, an automatic store redirect or an unresolved progress timer; those branches have regression coverage. Regeneration was disabled only in this one-cycle canary, while the production draw and regeneration method remain unchanged. The final compatibility correction changes only diagnostic inventory emission and returned listing metadata; its core flow matches the tested canary.
