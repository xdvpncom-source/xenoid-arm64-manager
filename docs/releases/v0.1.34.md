# v0.1.34: recoverable regeneration and memory headroom

Regeneration can resume a recorded Keybox preparation failure through the existing bootstrap owner. The operation retains its saved key, plan, profile and identity journal; ordinary healthy inspection is unchanged. A real interrupted operation completed with the same saved key and retired its journals. This is a host change and does not rebuild the Android runtime or change the input backend.

The optional `memory_reserve_mib` resource setting reserves reclaim headroom below the container's hard memory limit. Fresh 1 CPU / 2 GiB / 512 MiB swap devices default to 256 MiB. Existing fresh native `render_fps=15` policies also resolve a missing reserve field to 256 MiB; legacy display policies without native pacing keep zero, and explicit zero disables it. The existing resource reconciliation owns the cgroup-v2 `memory.high` receipt and bounded, fully reaped writer. Unknown administrator limits are preserved by rejecting conflicting changes. Hard CPU, memory and swap limits stay unchanged. This improves reclaim scheduling; it does not replace Android LMKD or guarantee that arbitrary apps fit in 2 GiB.

The QA scenario recognizes additional exact close-control IDs and contained duplicate accessibility controls, while keeping ambiguous controls rejected. Bounded, privacy-filtered failure evidence makes a later creative-specific failure diagnosable. All touches continue through official Xenoid input; there is no ADB input fallback and the uploaded APK is unchanged.

The candidate has focused regression and source-integrity coverage. Actual fleet qualification is recorded separately; this source release alone is not proof of a successful long-running test.
