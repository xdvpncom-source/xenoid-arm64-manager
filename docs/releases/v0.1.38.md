# v0.1.38: wait for native ownership without replaying input

A legitimate native operation can outlast the SDK's fixed six-second lock wait.
The saved workflow then reports a failed attempt even when its panel command
timeout is unlimited. A separate ad attempt exposed an observed Back button but
failed while reacquiring its fresh accessibility proof.

- Use the existing panel command budget for native ownership acquisition, with
  cancellation checks before entering the operation. Recheck the registered
  instance and running container after waiting. Never retry the protected body
  or input, and never extend an old navigation offer's lifetime.
- Reacquire a fresh Back proof once on the same synchronized reader only for
  four explicit provider-unavailable replies, within the existing offer and
  operation deadlines. Preserve the typed reply in diagnostics. Changed or
  ambiguous nodes, cleanup failures and lost input acknowledgements remain
  rejected. Final window, namespace, bounds, routing and mapping checks remain.
- After each Java navigation connection sets its service flags, allow a bounded
  platform bridge-settle wait before reading windows. A busy-UI idle timeout
  permits only the following actual node checks; it never establishes readiness.
  The flag4 wire format and the host's five-second offer lifetime are unchanged.
- During ordinary resource maintenance, read bootstrap readiness even when the
  proxy is healthy. A positively observed terminal component failure can invoke
  the existing owning bootstrap coordinator once. Invalidate earlier proxy
  readiness before that invocation; the next timer tick must prove it afresh.
  Resource, proxy and aggregate bootstrap readiness remain separate.

The small UI-reader JAR embedded in the Python helper is updated. No VPN APK,
Android image or native asset archive changes are included. Input continues
through the official Xenoid path. The live panel keeps
five desktop cards per row and a minimum ten-second request interval per device.
The current one-CPU/two-GiB resource configuration is unchanged.

Validation and actual rollout observations are recorded separately. Local
qualification includes real native flock contention across separate processes,
cancellation during acquisition, fresh ordered-pipe navigation requests and
post-bootstrap epoch/proxy counterexamples. The earlier fleet observation's
three failed attempts remain recorded and are not relabeled as successful.

The final source passed 1,258 tests (1,250 passed, eight platform skips). The
embedded JAR was built twice identically and passed eight compiled-Java tests.
On a production one-CPU/two-GiB canary, the new reader returned an actual fresh
SystemUI Back proof in 1.799 seconds on the VPN main activity, within the unchanged
five-second limit. Its private helper and launcher exited, the original runtime
binding and source hashes stayed unchanged, and the normal panel workflow was
restored. That canary sent no input and does not establish advertisement closure;
ordinary fleet workflow observations are a separate qualification.
