# v0.1.48 — finish ad recovery after fast redirects and late clear reads

A fast advertisement redirect can reach the configured store between UI observations. After the completed post-Connect dwell, the scenario now permits one fresh, verified official Android Back action from a package explicitly listed in `AD_LANDING_PACKAGES`, even without a previously observed ad activity. It does not invent an origin or authorize a second origin-specific Back. Setting `AD_LANDING_REQUIRE_OBSERVED_AD=True` restores the stricter observed-origin requirement.

Sometimes the first clear app hierarchy returns just as its observation deadline expires. Ad dismissal and startup preparation now get one bounded read-only confirmation when their final observation was a stable, clear app window. The returned snapshot must still be clear and arrive within `AD_FINAL_READY_VERIFY_SECONDS` (30 seconds by default). This phase sends no input and grants no additional ad-action budget; a returned ad or unverified window still fails.

Final UI-reader teardown also waits for the existing native owner instead of failing after a fixed twelve-second lock wait. Ordinary reader cleanup uses the configured command budget; final round cleanup retains the same reader until it can acquire the lock and close safely. Only the exact native lock-entry contention error is retried. The close operation itself, unrelated errors and an explicit shutdown are never replayed or suppressed.

Fresh resource defaults now use `memory_reserve_mib=0`, removing the earlier 1,792-MiB soft-throttling threshold. The actual container limit remains 2 GiB RAM, one CPU and 512 MiB swap. Explicit saved reserve values, including 256 MiB, remain valid and unchanged; an existing fleet policy must be updated through the panel to opt into the new default. The existing verified resource writer and recovery receipts are preserved.

The full UI inventory, countdown/progress handling, official Xenoid touch mapping, app assignment, cleanup and successful-cycle regeneration sequence remain unchanged. Tests cover missed store redirects, pre-dwell and unconfigured-package rejection, absence of fabricated origin, late clear and non-clear reads, and a confirmation read that exceeds its own deadline. Live qualification is recorded separately.

The assigned-APK canary completed one cycle with five official input actions, a requested 120-second post-permission wait, two observed ad-close actions and successful close/data cleanup. The first ad-close action occurred 126.591 seconds after the wait started; the final foreground hold lasted 10.233 seconds. No error or countdown fallback occurred in this run. Regeneration was disabled only in the one-cycle canary. The cleanup-lock change has a separate real-process contention test, and the soft-memory change was qualified through two successful cycles with the hard 2-GiB limit unchanged.
